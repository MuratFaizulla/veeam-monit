# Veeam Telegram Monitor

Сервис на NestJS, который следит за Veeam Backup & Replication через его REST API
и присылает в Telegram **только изменения**: новые ошибки и предупреждения заданий,
их восстановление, пропажу и возврат связи с сервером, отказ служебной учётной
записи и нехватку места в репозиториях. Плюс темы с живым состоянием,
которые всегда показывают текущую картину одним сообщением.

> **Ветка `telegram-only`.** Здесь нет веб-дашборда: удалены React-фронтенд,
> браузерные сессии и все read-эндпоинты, которые его обслуживали
> (`/api/jobs`, `/api/dashboard`, `/api/infrastructure`, `/api/backups`,
> `/api/replicas`, `/api/compliance`, `/api/reports`, `/api/auth`).
> Полная версия с дашбордом осталась в ветке `main`.

## Что осталось

```
backend/src/
  telegram/            маршрутизация, темы, транспорт, состояние, монитор
  veeam/               транспорт к Veeam REST API, типы, ошибки
  config/              чтение переменных окружения
  logging/             файловый лог и тайминги запросов
  health.controller.ts неаутентифицированная проба доступности
```

## Требования

- Node.js 20+
- Доступ по сети до Veeam Backup & Replication (порт 9419)
- Служебная учётная запись Veeam — достаточно роли Veeam Backup Viewer
- Бот в Telegram, добавленный в группу администратором

## Запуск

```bash
cd backend
npm install
cp .env.example .env     # заполнить токен бота и учётную запись Veeam
npm run start:dev        # или npm run build && npm run start:prod
```

Проверки: `npm run lint` (`tsc --noEmit`) и `npm test` (сборка + `node:test`).

## Настройки

Все параметры с комментариями — в `backend/.env.example`. Минимум для старта:

VEEAM_MONITOR_USERNAME=<служебная учётная запись>

## HTTP-поверхность

Осталось два набора маршрутов — проба и управление мониторингом:

- `GET /api/health` — неаутентифицированная проба: отвечает ли Veeam вообще.
- `GET|POST /api/telegram/*` — см. раздел «Эндпоинты» ниже.

## Как работает маршрутизация

### Маршрутизация по темам (topics)

Группа-форум (супергруппа с включёнными темами) — это одна `chat_id` и много
`message_thread_id`. Сообщение без `message_thread_id` всегда попадает в
**General**, поэтому раньше туда сваливалось всё подряд. Теперь каждое событие
проходит через маршрутизатор и получает свою тему.

| Режим `TELEGRAM_ROUTING_MODE` | Куда попадают события |
| --- | --- |
| `single` (по умолчанию) | всё в General; набор тем фиксирован |
| `job` | каждое задание — в собственную тему с именем задания; инфраструктура, репозитории и сводки — в темы своих категорий |
| `severity` | по важности: ошибки, предупреждения, восстановления, события |
| `kind` | по категориям; все задания делят одну тему |

Бот создаёт недостающие темы сам — для этого ему нужно право **«Управление
темами»** в группе. Если права нет, он один раз пишет об этом в лог и продолжает
отправлять в General, а не молчит. Темы, созданные людьми вручную, бот узнаёт из
апдейтов: Bot API не умеет перечислять темы, поэтому имя темы становится
известно, только когда бот видит её создание или команду в ней.

Соответствие «тема → `message_thread_id`», последние результаты заданий и
активные кулдауны лежат в `backend/data/telegram-state.json`. Файл переживает
перезапуск: без него бэкенд заново создавал бы темы-дубликаты и либо повторял бы
старые аварии, либо молча пропускал первый цикл.

### Какие темы появятся

При настройках по умолчанию (`TELEGRAM_ROUTING_MODE=single`) набор тем
**фиксирован** и не растёт со временем:

- `General` — все уведомления: ошибки и восстановления заданий, связь с Veeam,
  репозитории, сводки, ручные сообщения;
- `🩺 Monitor health`, `▶️ Running now`, `📅 Today`, `📈 Performance`,
  `💾 Repositories`, `🛡 Protection`, `🗂 Restore points`,
  `🧹 Orphaned backups` — живые статусы, см. ниже.

Режим `job` (бывший по умолчанию) заводит отдельную тему на каждое задание,
которое хоть раз сменило результат. На установке со 112 заданиями список тем
перестаёт читаться, поэтому по умолчанию он больше не включён. Режимы
`severity` и `kind` дают промежуточные варианты: темы `🔴 Errors`,
`🟡 Warnings`, `🟢 Recovered`, `ℹ️ Events` либо `📦 Jobs`, `🖥 Infrastructure`,
`💾 Repositories`, `🛡 Security`, `📊 Daily digest`, `📣 Announcements`.

Живые статусы от режима не зависят: они не события и через маршрутизатор не
проходят вообще.

Тонкая настройка — в `TELEGRAM_ROUTES_FILE`: список правил, где первое
совпавшее выигрывает. Правило умеет задавать тему, ограничивать событие одним
чатом или глушить его совсем. Образец — `backend/telegram-routes.example.json`,
применяется без перезапуска через `POST /api/telegram/routes/reload`.

### Живые статусы: одно сообщение вместо ленты

Эти темы устроены иначе, чем все остальные. В них лежит **ровно одно сообщение**,
которое правится на месте, а не дописывается новым:

- `🩺 Monitor health` — работает ли мониторинг прямо сейчас: связь с Veeam,
  авторизация служебной учётной записи, сколько заданий под наблюдением, когда
  была последняя проверка и что показывают часы самого сервера.
- `▶️ Running now` — какие задания идут в эту секунду, с процентом,
  временем старта и длительностью. Если не идёт ни одного — так и написано,
  и только тогда показывается ближайший запуск: это единственный момент, когда
  вопрос «что дальше» задают именно здесь.
- `📅 Today` — что ещё сегодня стартует по расписанию, списком по времени.
  Если на сегодня больше ничего — показывается ближайший запуск за пределами
  суток.
- `🛡 Protection` — что на самом деле не защищено: у кого нет свежей точки
  восстановления и у кого несколько неудачных запусков подряд.
- `🗂 Restore points` — сколько точек у каждого задания, когда снята последняя
  и сколько запусков оно пропустило против собственного ритма.
- `🧹 Orphaned backups` — цепочки, у которых не осталось задания: сколько в них
  точек и когда в них писали последний раз.

### 🗂 Restore points — кто отстал от собственного расписания

`🛡 Protection` отвечает на вопрос «есть ли свежая точка вообще» и показывает
только нарушителей. Эта тема показывает **все** задания, которые должны
работать, и по каждому — то, что спрашивают у задания в первую очередь: сколько
точек, когда снята последняя и не пропустило ли оно с тех пор запуски.

```
🔴 PLT_TTC_Netflow — 4 точки · пропущено 4 запуска · 22 августа 2026 г. в 22:09:08
🟠 TTC_DC — 8 точек · пропущен 1 запуск · 10 сентября 2026 г. в 02:17:58
🟢 TTC_SOC_vms — 18 точек · 13 сентября 2026 г. в 22:01:28
```

Пропуск считается **по собственному ритму задания**, а не по календарю: два дня
без точки для еженедельного задания — норма, для ночного — два пропущенных
бэкапа. Одно и то же число дней означает противоположные вещи, поэтому список
отсортирован по пропущенным запускам, а не по возрасту. Ритм берётся как медиана
интервалов между последними прогонами; когда прогонов слишком мало, ритм
неизвестен — такая строка помечается `⚪`, и про пропуски у неё не утверждается
ничего.

Задания **без расписания** и **выключенные** в список не входят: им нечего
пропускать. Сколько их — сказано в подвале, чтобы список не уменьшался молча.

Дата пишется полностью, а не как «5 дней назад»: это строка, которую читают
перед тем, как открыть Veeam, а относительный возраст приходится переводить
обратно в дату, прежде чем с чем-то сверить. Когда всё не помещается,
обрезаются те, кто идёт по графику, и их число названо.

Данные берутся из того же сканирования, что и `🛡 Protection`, поэтому
дополнительных запросов к Veeam эта тема не добавляет.

### 🧹 Orphaned backups — что осталось от удалённых заданий

Удаление задания в Veeam не удаляет то, что оно создало: бэкап и его точки
остаются на репозитории. Увидеть их нечем — **все** остальные проверки идут от
списка заданий, а у этих цепочек задания нет. На этой установке так лежит
больше половины всех точек восстановления.

Тема показывает цепочки от самых больших, с числом точек и датой последней
записи. Цвет — по возрасту последней точки: до 30 дней, до 90, дальше.

Автоматически ничего не удаляется и удалять не предлагается: цепочка, оставленная
намеренно после вывода задания из эксплуатации, выглядит ровно так же, как
забытая. Отличить их может только человек.

### 🛡 Protection — единственная проверка, которая не про «что сломалось»

Все остальные уведомления срабатывают на **переход**: задание было в порядке и
перестало. Это оставляет самый опасный случай невидимым — задание со статусом
`Success`, у которого последняя точка восстановления от июня, потому что оно
просто перестало запускаться. Ничего не переходит, значит ничего и не
сообщается, и дыра обнаруживается в момент, когда нужно восстановиться.

Поэтому этот слот спрашивает не статус задания, а сами точки восстановления
(`/api/v1/restorePoints`), и привязывает их к заданиям через `/api/v1/backups`.

Задание попадает в список, если выполнено любое из двух:

- новейшая точка старше **и** порога `TELEGRAM_PROTECTION_STALE_DAYS`,
  **и** `TELEGRAM_PROTECTION_OVERDUE_FACTOR` × собственного интервала задания;
- подряд `TELEGRAM_PROTECTION_FAILURE_STREAK` неудачных **запусков**, даже если
  точка свежая.

Не учитываются выключенные задания и задания без расписания: они и не должны
ничего производить. Сколько таких — написано в самом сообщении, чтобы
сократившийся счётчик не выглядел как «всё починилось».

Запуск — не сессия. Veeam сам перезапускает упавшее задание, и каждый повтор
приходит отдельной сессией: при стандартных трёх повторах один упавший запуск
выглядит как четыре неуспеха. Сессии, стоящие ближе друг к другу, чем окно
повторов задания, сворачиваются в один запуск — без этого «4 неуспеха подряд»
стояло почти у каждого падающего задания и не значило ничего.

Второе условие в первом пункте важно: плоский порог «3 дня» врёт на заданиях,
которые по расписанию и так реже. Свой интервал считается как медиана
промежутков между последними точками самого задания — медиана, а не среднее,
чтобы один долгий простой не переопределил недельное задание в месячное.

Сканирование читает все точки восстановления — порядка 20 запросов и несколько
секунд, — поэтому идёт на своей медленной частоте
(`TELEGRAM_PROTECTION_INTERVAL_MIN`, по умолчанию 30 минут). Кэшируются при этом
сырые данные, а не вердикт: вердикт пересчитывается каждый цикл по текущим
часам, поэтому возраст в сообщении остаётся верным между сканированиями.

Расписание вынесено отдельно намеренно. Оно меняется редко, а `Running now`
переписывается каждую минуту, пока идут задания; и при десяти активных заданиях
добавлять к ним ещё и весь список предстоящих — значит получить сообщение,
которое никто не дочитывает. Разделение заодно убирает дублирование: строка
«ближайший запуск» живёт в одном месте, а не в двух, которые могут разойтись.

Причина такого устройства: состояние — это не событие. Раньше «монитор запущен»
уходило как обычное уведомление, и шесть перезапусков подряд давали шесть
одинаковых сообщений, ни одно из которых не отвечало на вопрос «а сейчас-то
работает?». Теперь `id` сообщения хранится в файле состояния, поэтому
перезапуск продолжает то же самое сообщение, а не заводит второе. Если
сообщение удалили в Telegram, остаток подчищается и слот занимает новое.

Сообщение не переписывается, пока его содержимое не изменилось: строка
«Обновлено» в сравнении не участвует, иначе правка уходила бы каждую минуту
просто так. Раз в `TELEGRAM_LIVE_REFRESH_MIN` минут сообщение обновляется в
любом случае — застывшая отметка времени означает, что встал сам монитор.

Выключается через `TELEGRAM_LIVE=false`; имена тем — `TELEGRAM_TOPIC_HEALTH`,
`TELEGRAM_TOPIC_RUNNING`, `TELEGRAM_TOPIC_SCHEDULE` и
`TELEGRAM_TOPIC_PERFORMANCE`, часовой пояс отображения — `TELEGRAM_TIMEZONE`.

### 📈 Performance

Тема Performance содержит одно постоянно актуальное сообщение о самых медленных
активных заданиях. Монитор собирает активные сессии с пагинацией, читает их
`taskSessions` не более чем по пять одновременно и редактирует сохранённый
`message_id`. Неизменившийся текст повторно не отправляется. Удалённое сообщение
создаётся заново; попытка закрепления выполняется без остановки мониторинга при
недостатке прав.

Для заранее созданной темы укажите её идентификатор:

```env
TELEGRAM_TOPIC_PERFORMANCE=📈 Performance
TELEGRAM_PERFORMANCE_TOPIC_ID=123
```

Чтобы определить `message_thread_id`, откройте тему Performance и отправьте в ней
`/status`: в ответе поле «Топик» содержит нужное число. Команда `/topics` выводит
все темы, которые бот уже создал или увидел. Если оставить идентификатор пустым,
бот попробует создать тему самостоятельно; для этого ему требуется право
«Управление темами».

Veeam REST API предоставляет текущую скорость `processingRate`, объёмы
`processedSize`, `readSize`, `transferredSize`, общий прогресс и категорию
`bottleneck`. API не предоставляет отдельные проценты нагрузки Source, Proxy,
Network и Target, поэтому монитор их не вычисляет и не показывает.

### 💾 Repositories

Отдельная live-тема показывает заполнение, общую ёмкость, свободное место и
фактическое поле `isOnline` для каждого репозитория. Репозитории сортируются по
заполнению, сообщение сохраняется и редактируется только при изменениях.

```env
TELEGRAM_TOPIC_REPOSITORIES_LIVE=💾 Repositories
TELEGRAM_REPOSITORIES_TOPIC_ID=456
```

Идентификатор определяется командой `/status`, отправленной внутри темы. Если
оставить его пустым, бот создаст тему при наличии права управления темами.

### Защита от шума и лимитов

- Одно событие на **переход** статуса, а не на каждый опрос. Успех сообщается
  только как восстановление после ошибки.
- Постоянные проблемы (сломанный вход, заполненный репозиторий) повторяются не
  чаще, чем раз в свой кулдаун (`TELEGRAM_*_COOLDOWN_MIN`).
- Отправка сериализована по чатам, с паузой `TELEGRAM_SEND_INTERVAL_MS`; ответ
  `429` ставит очередь этого чата на паузу ровно на `retry_after` секунд.
- Сообщения уходят с `parse_mode=HTML` и экранированием, поэтому имя задания с
  `_`, `*` или `<` не ломает отправку.
- Если тему удалили, бот забывает её `message_thread_id`, создаёт заново и
  повторяет отправку.

### Настройка

```env
TELEGRAM_BOT_TOKEN=<токен из BotFather>
TELEGRAM_CHAT_IDS=-1001234567890
TELEGRAM_ADMIN_KEY=<длинная случайная строка>
TELEGRAM_ROUTING_MODE=single
TELEGRAM_MONITOR_INTERVAL_MS=60000
VEEAM_MONITOR_USERNAME=<служебная учётная запись>
VEEAM_MONITOR_PASSWORD=<её пароль>
```

Полный список параметров с комментариями — в `backend/.env.example`.

`TELEGRAM_WEBHOOK_URL` не обязателен: пустое значение включает long polling, для
которого не нужны домен, публичный IP, сертификат и правило на файрволе. Если
значение задано, оно должно быть публичным HTTPS-origin — бэкенд сам
зарегистрирует `https://<origin>/api/telegram/webhook` при старте.

`VEEAM_MONITOR_USERNAME` / `VEEAM_MONITOR_PASSWORD` — отдельная служебная учётная
запись (роль Veeam Backup Viewer достаточно). Без неё монитор видит только
доступность API и честно об этом пишет; состояние заданий не отслеживается.

### Порядок ввода в эксплуатацию

1. Создать бота в BotFather, добавить в группу и выдать права администратора,
   включая «Управление темами».
2. Включить в группе темы (Topics) — иначе весь трафик останется в General.
3. Прописать `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_IDS`, `TELEGRAM_ADMIN_KEY` и
   служебную учётную запись Veeam, запустить бэкенд.
4. Проверить `GET /api/telegram/status`: `enabled`, режим, число чатов,
   `monitor.authenticated`.
5. Прогнать маршрутизацию вхолостую:
   `POST /api/telegram/test` с `{"kind":"job","severity":"critical","subject":"Имя задания"}`
   — в группе должна появиться тема с этим именем и сообщение в ней.
6. `POST /api/telegram/check` — принудительный цикл опроса Veeam.

### Один экземпляр бота

Telegram отдаёт апдейты только одному читателю: если одновременно запущены два
бэкенда с одним токеном (например `npm run start:dev` и `npm run start:prod`), в
логе появится `409 Conflict: terminated by other getUpdates request`, а команды в
группе начнут теряться. Отправка уведомлений при этом работает у обоих, то есть
сообщения уйдут дважды. В проде должен работать ровно один экземпляр; если нужен
второй — у него должны быть пустой `TELEGRAM_BOT_TOKEN` или
`TELEGRAM_MONITOR_INTERVAL_MS=0`.

### Первый запуск и текущие аварии

Первый цикл молча запоминает текущие результаты всех заданий — иначе старт на
инсталляции с десятками давно падающих заданий высыпал бы сотню сообщений сразу.
Сообщаться будут только последующие изменения. Чтобы увидеть картину целиком,
включите ежедневную сводку через `TELEGRAM_DIGEST_HOUR`.

### Эндпоинты

Все, кроме `status` и `webhook`, защищены заголовком `X-Telegram-Admin-Key`.

- `GET /api/telegram/status` — готовность интеграции, режим, очередь отправки и
  здоровье монитора (доступность Veeam, вход служебной записи, число заданий).
- `POST /api/telegram/webhook` — колбэк Telegram, защищён заголовком
  `X-Telegram-Bot-Api-Secret-Token`.
- `GET /api/telegram/chats` — зарегистрированные чаты и известные темы.
- `GET /api/telegram/routes` — действующая таблица маршрутизации.
- `POST /api/telegram/routes/reload` — перечитать файл правил.
- `POST /api/telegram/notify` с `{ "text": "..." }` — произвольное сообщение.
- `POST /api/telegram/test` — синтетическое событие через реальный маршрутизатор.
- `POST /api/telegram/check` — немедленный цикл проверки Veeam.

В самой группе бот отвечает на `/start`, `/status`, `/chatid` (выводит `chat_id`
и `message_thread_id` текущей темы) и `/topics` (список известных тем).
